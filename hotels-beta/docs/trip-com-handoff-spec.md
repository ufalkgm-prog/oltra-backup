# Trip.com affiliate handoff — implementation spec

Purpose: myOLTRA's AI concierge presents flight options from its own data source
(Duffel or Amadeus). When a member chooses to book, we hand them off to Trip.com
with the search pre-filled and our affiliate tracking attached. Trip.com is
merchant of record. myOLTRA never takes payment and never creates a booking.

---

## 1. Verified URL pattern

Captured from a live Trip.com search (Copenhagen to Sydney, business class,
2 adults + 1 child, round trip):

```
https://www.trip.com/flights/showfarefirst
  ?dcity=cph
  &acity=syd
  &ddate=2026-10-22
  &rdate=2026-10-31
  &dairport=cph
  &triptype=rt
  &class=c
  &quantity=2
  &childqty=1
  &nonstoponly=off
  &locale=en-XX
  &curr=DKK
  &lowpricesource=searchform
  &searchboxarg=t
```

### Parameter reference

| Parameter | Value seen | Meaning | Confidence |
|---|---|---|---|
| `dcity` | `cph` | Departure city, lowercase IATA | Verified |
| `acity` | `syd` | Arrival city, lowercase IATA | Verified |
| `dairport` | `cph` | Specific departure airport | Verified |
| `ddate` | `2026-10-22` | Outbound date, `YYYY-MM-DD` | Verified |
| `rdate` | `2026-10-31` | Return date, `YYYY-MM-DD` | Verified |
| `triptype` | `rt` | `rt` round trip, `ow` one-way, `mt` multi-city | Verified |
| `class` | `c` | Cabin. See cabin codes below | Partially verified |
| `quantity` | `2` | Adult count | Verified |
| `childqty` | `1` | Child count | Verified |
| `babyqty` | `0` | Infant count | Verified |
| `nonstoponly` | `off` | Direct-only filter | Verified |
| `locale` | `en-XX` | Language / locale | Verified |
| `curr` | `DKK` | Display currency | Verified |
| `lowpricesource` | `searchform` | Origin of search | Cosmetic, safe to include |
| `searchboxarg` | `t` | Internal flag | Cosmetic, safe to include |

### Cabin codes (`class`)

| Code | Cabin | Status |
|---|---|---|
| `y` | Economy | Verified |
| `s` | Premium Economy | Verified |
| `ys` | Economy + Premium Economy combined | Verified |
| `c` | Business | Verified |
| `f` | First | Verified |

Map the member's requested cabin to the single-cabin code (`y`, `s`, `c`, `f`).
Use `ys` only if the concierge deliberately wants to show economy and premium
economy together, for example when presenting a price-conscious comparison.

### One-way

Set `triptype=ow`. Trip.com's own front end still emits a stale `rdate` on
one-way searches and ignores it. Omit `rdate` when building one-way links; if
any problem appears, including a throwaway value is demonstrably tolerated.

### Multi-city

Set `triptype=mt` and replace the single-leg parameters with zero-indexed groups,
one per leg. Verified example, Copenhagen to Sydney to Christchurch to
Copenhagen:

```
multdcity0=cph&multacity0=syd&dairport0=cph&multddate0=2026-10-22
multdcity1=syd&multacity1=chc&aairport1=chc&multddate1=2026-10-28
multdcity2=chc&multacity2=cph&dairport2=chc&multddate2=2026-11-02
```

Per leg `n`:

| Parameter | Meaning |
|---|---|
| `multdcity{n}` | Departure city, lowercase IATA |
| `multacity{n}` | Arrival city, lowercase IATA |
| `multddate{n}` | Departure date, `YYYY-MM-DD` |
| `dairport{n}` | Specific departure airport, optional |
| `aairport{n}` | Specific arrival airport, optional |

`class`, `quantity`, `childqty`, `babyqty`, `nonstoponly`, `locale` and `curr`
remain single, top-level parameters and are not indexed. Do not send `ddate`,
`rdate`, `dcity` or `acity` on a multi-city link.

The airport parameters appeared inconsistently in the captured example
(`dairport0`, `aairport1`, `dairport2`), which suggests they are optional and
emitted only where the search form had a specific airport rather than a city.
Send them only where the member specified an airport.

### Airline filter — not available

Confirmed by testing: filtering to a carrier on the results page changes page
state only and leaves the URL unchanged. There is no way to hand a member off to
a single airline's results. See section 4 for how to compensate.

Case sensitivity: Trip.com accepts both `triptype=rt` / `class=c` (search form)
and `triptype=RT` / `class=C` (later pages). An earlier affiliate-generated link
used `flighttype=S` with uppercase city codes. All forms appear tolerated.
Standardise on the lowercase search-form variant, since that is what their own
search box produces.

## 2. Affiliate tracking parameters

Append these to every generated URL. Values are constant except `trip_sub1`.

```
&Allianceid=10501597
&SID=330783916
&trip_sub3=D19756963
&trip_sub1=<placement-label>
```

- `Allianceid` — myOLTRA's affiliate account.
- `SID` — the myOLTRA site profile.
- `trip_sub3` — generated by Trip.com's link builder. Purpose undocumented.
  Include it as-is until Trip.com confirms whether it is required on
  dynamically constructed links.
- `trip_sub1` — free-text placement label, used for reporting. Use a stable
  vocabulary, e.g. `concierge-chat`, `flight-results`, `trip-summary`,
  `email-followup`.

## 3. Implementation

Build a single function that takes the itinerary the member selected in the
concierge and returns a tracked Trip.com URL.

Input shape. Model the itinerary as a list of legs so that one-way, round trip
and multi-city are the same structure rather than three code paths:

```
{
  legs: [
    { origin: "CPH", destination: "SYD", date: "2026-10-22",
      originAirport: "CPH", destinationAirport: null },
    { origin: "SYD", destination: "CHC", date: "2026-10-28",
      originAirport: null, destinationAirport: "CHC" }
  ],
  cabin: "business",        // economy | premium | business | first
  adults: 2,
  children: 1,
  infants: 0,
  directOnly: false,
  currency: "DKK",
  placement: "concierge-chat"
}
```

Trip type is derived, not passed in:

- One leg, `triptype=ow`, single-leg parameters.
- Two legs that mirror each other (leg 2 origin equals leg 1 destination and
  vice versa), `triptype=rt`, single-leg parameters with `rdate` from leg 2.
- Anything else, `triptype=mt`, indexed parameters.

Requirements:

- Lowercase the IATA codes.
- Map cabin names to `class` codes via a lookup table, so the codes live in one
  place: `economy` → `y`, `premium` → `s`, `business` → `c`, `first` → `f`.
- Set `nonstoponly=on` when the itinerary the member chose is non-stop. This is
  the only filter available that meaningfully narrows the results list, so use
  it whenever it is accurate.
- Default `curr` to `DKK`, but make it configurable per member.
- Default `locale` to `en-XX`. If Danish-language landing pages are wanted
  later, this is the single switch.
- URL-encode all values.
- Open in a new tab, with `rel="noopener"`.

Do not scrape Trip.com, and do not construct URLs by string-replacing a stored
example. Build them from parameters.

## 4. Known limitation: search, not offer

The deep link lands the member on a **filtered search results page**, not on the
specific flight the concierge recommended. The member re-selects on Trip.com.

**This is a hard limit, not a gap in our research.** Trip.com's post-selection
URL (`/flights/passenger`) was inspected and cannot be reconstructed. It carries
three pieces of server-generated session state:

- `remarkTokenKey` — an opaque hash.
- `shortPolicyId` — a fare-policy identifier with the search timestamp embedded
  (e.g. `...20260909212959...`), tied to the session that produced it.
- `txid` — a transaction identifier.

These expire. A URL of this form is the output of a live search on Trip.com's
own system and cannot be generated from a member's chosen itinerary. Do not
attempt to template it.

Consequences for the concierge layer:

- Phrase the handoff as taking the member to the relevant options, never as
  booking a specific flight. For example: "I'll take you to the Thai Airways
  business class options for these dates" rather than "book this flight".
- **There is no airline filter parameter.** Confirmed by testing: filtering to a
  carrier on the results page changes page state only and leaves the URL
  unchanged. A member cannot be handed off to a single airline's results.
- Narrow the results with the filters that *are* in the URL. `class` already
  restricts the cabin. Set `nonstoponly=on` whenever the itinerary the member
  chose is non-stop; this typically cuts the results list dramatically and often
  leaves only a handful of carriers.
- Compensate in the concierge copy. The message accompanying the handoff must
  name the carrier and the flight numbers, so the member is matching against
  something specific rather than re-deciding. For example: "This is Thai Airways
  TG951 and TG471 outbound, TG476 and TG950 returning. I'll open the business
  class results for these dates so you can select it."
- Consider showing the member the expected price alongside the flight numbers,
  so they can confirm they have found the right itinerary on Trip.com.
- Prices shown by myOLTRA come from a different source than Trip.com's. Label
  them as indicative and expect differences. Never present a myOLTRA price as
  the price the member will pay.

## 5. Test checklist before launch

1. Generate a link through the function and click it. Confirm the Trip.com
   results page matches the requested route, dates, cabin and passenger counts.
2. Confirm the click registers in the Trip.com affiliate dashboard. This is the
   critical test: it proves tracking survives a hand-built URL.
3. Repeat with a different `trip_sub1` and confirm the two are distinguishable
   in reporting.
4. Test one-way, round trip, multi-city, multi-passenger with an infant, and
   each of the four cabin classes.
5. Test on mobile, where Trip.com may attempt to open its app.
6. Test a date far enough ahead that no flights are loaded yet, and confirm the
   page degrades sensibly rather than erroring.

## 6. Open question for Trip.com

Confirm in writing that constructing deep links programmatically from member
input is permitted under the affiliate terms, and whether `trip_sub3` must be
present. Deep linking is normally allowed and scraping is what is prohibited,
but get it on record before building on it.
